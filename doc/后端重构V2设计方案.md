# 后端重构V2设计方案

## 1. 文档定位

本文档只用于说明后端 V2 重构的设计口径和边界。

本次 V2 不是在原项目上直接修改，而是在新建 `V2` 目录中重做。旧后端的作用不仅是问题定位和逻辑参考来源，也是数据库契约的基线来源。V2 可以在分层、命名、接口组织和任务拆分上优化，但必须完全复用旧项目既有数据库、表结构、字段语义、数据来源和核心关联关系，不能脱离旧库另起一套存储模型。

## 2. 重构前提

1. V2 在新目录中重做，原项目保留作为参考。
2. V2 对外接口对标前端真实使用的 API。
3. V2 接口规范只使用 `GET` 和 `POST`。
4. 如果当前前端存在 `PUT` 或 `DELETE`，则前端也需要同步调整。
5. V2 的业务逻辑必须参考旧项目已有实现，允许结构优化和逻辑优化，但不得脱离旧项目既有业务语义。
6. V2 的数据库必须完全复用旧项目，不能修改底层数据库资产、既有表结构契约和既有数据来源。
7. V2 重构范围不仅包含接口，也包含定时任务、数据同步、自动预警等非接口能力。

## 3. 重构范围

| 范围 | 说明 |
| --- | --- |
| 接口层 | 对标 `frontendV2` 真实使用的 API，重新设计 V2 接口 |
| 业务逻辑层 | 参考旧后端已有实现，必要时优化，不做机械搬运 |
| 数据库契约 | 完全复用旧项目既有数据库、表结构、字段语义、数据源划分和核心关联关系 |
| 定时任务 | 旧后端中的自动预警、数据同步等任务需要纳入 V2 范围 |
| 外部依赖 | 包括外部监测接口、数据采集来源、第三方调用方式 |
| 权限与资源 | 用户、角色、菜单、字典等基础支撑能力 |
| 数据处理细节 | 多数据源、几何点位、SQL Server 特殊处理、上传导出等 |

V2 重点涉及模块：

1. 系统管理
   - 用户
   - 角色
   - 菜单
   - 字典
2. 预警管理
   - 预警信息
   - 预警指标
   - 预警设施
   - 自动预警任务
3. 工程管理
   - 监测站点
   - 监测项
   - 防洪预案
4. 巡检与养护
5. 水雨情、大坝、闸门
6. 数据同步与外部采集任务

## 4. 设计原则

### 4.1 新目录重做

V2 独立建设，不在旧目录上做增量拼接。

### 4.2 接口统一规范

V2 只使用两种请求方式：

1. `GET`
   - 用于查询
2. `POST`
   - 用于新增、修改、删除、批量处理和特殊业务动作

说明：

1. V2 不使用 `PUT`
2. V2 不使用 `DELETE`
3. 如果前端现有调用不符合该规范，则前端必须同步调整

#### 4.2.1 统一前缀与资源命名

1. 所有 V2 接口统一挂在 `${jzsk.v2.api-prefix}` 下，默认前缀为 `/api`
2. 前端 `frontendV2` 中的 API 封装统一显式书写 `/api` 前缀，`baseURL` 只承担主机和端口，不再额外拼接路径前缀
3. 资源路径统一使用小写英文复数 + `kebab-case` 命名，例如：
   - `/api/users`
   - `/api/roles`
   - `/api/measuring-stations`
   - `/api/warning-indicators`
4. 禁止继续沿用 `info`、`search-list`、`add`、`LVs` 这类历史混合命名作为 V2 正式路径

#### 4.2.2 标准路径模板

| 类型 | 方法 | 标准路径 |
| --- | --- | --- |
| 分页查询 | `GET` | `/api/{resources}/page` |
| 普通列表 | `GET` | `/api/{resources}/list` |
| 详情查询 | `GET` | `/api/{resources}/{id}` |
| 新增 | `POST` | `/api/{resources}/create` |
| 修改 | `POST` | `/api/{resources}/update` |
| 删除 | `POST` | `/api/{resources}/delete` |
| 批量删除 | `POST` | `/api/{resources}/batch-delete` |
| 选项列表 | `GET` | `/api/{resources}/options` |
| 导出 | `GET` | `/api/{resources}/export` |
| 上传 | `POST` | `/api/{resources}/upload` |

说明：

1. 删除操作统一通过请求体传递 `id` 或 `ids`，不再使用 `DELETE /{id}`
2. 批量动作统一使用动作型后缀，例如 `/batch-delete`
3. 特殊业务动作允许单独建动作路径，但必须使用可读动作名，不得混用旧表名和旧方法名

#### 4.2.3 分页与查询参数规范

1. 分页查询统一使用 `page`、`size`
2. V2 不再新增 `currentPage/pageSize`、`current/size` 这类并行口径
3. 普通筛选条件一律使用查询参数透传，不为“搜索”单独设计 `search-list` 接口
4. 如查询条件复杂到不适合 URL 传参，可额外提供 `POST` 查询接口，但必须在模块内单独说明，不作为默认口径

#### 4.2.4 返回结构规范

1. 所有接口统一返回 `ApiResult<T>`
2. 分页数据统一返回 `PageResultVO<T>`，字段固定为：
   - `list`
   - `total`
   - `page`
   - `size`
   - `totalPages`
3. 不再以 V2 正式契约形式输出 `records`、`currentPage`、`current` 等旧字段

#### 4.2.5 特殊动作命名规范

以下场景允许在资源路径下使用动作后缀：

1. 权限分配：`/assign`
2. 密码重置、密码修改：`/reset`、`/update`
3. 巡检处理、预警解除等业务动作：使用明确业务动词，例如 `/solve`、`/clear`
4. 字典树形选项、扁平选项：使用 `/options/tree`、`/options/list`

动作接口仍然必须遵循：

1. 查询使用 `GET`
2. 变更使用 `POST`
3. 请求体使用 DTO，不直接传 `Map` 或裸数组作为长期正式口径

#### 4.2.6 认证与当前用户接口边界

1. `auth` 资源承担认证域能力，至少包含 `POST /api/auth/login` 和 `GET /api/auth/current-user`
2. `GET /api/auth/current-user` 固定用于获取当前登录用户信息，不接受用户 ID，不复用后台用户管理详情接口
3. `/api/users/{id}` 固定为后台用户管理详情接口，只用于按 ID 查询指定用户
4. 前端认证状态恢复、首页个人信息展示和当前用户识别统一依赖 `GET /api/auth/current-user`
5. 禁止将“当前用户”与“按 ID 用户详情”继续混用为同一个接口语义或同一个前端方法名

#### 4.2.7 菜单静态配置边界

当前 `frontendV2` 的页面导航菜单继续使用前端静态数据维护，作为现阶段唯一菜单来源。

因此当前阶段：

1. 不建设 `backendV2` 的动态菜单管理接口
2. 不将菜单接口迁移作为 D1 的必做项
3. 如后续出现按角色动态裁剪导航、后台持久化维护菜单等真实需求，再单独评估是否纳入 V2 后端范围

### 4.3 旧项目逻辑参考与数据库复用原则

旧后端承担三类价值：

1. 作为问题定位来源
2. 作为已有业务处理经验来源
3. 作为数据库契约基线来源

V2 必须完全复用旧项目数据库契约：

1. 复用既有数据库和表结构
2. 复用字段语义、主外键关系和核心关联关系
3. 复用既有认证、权限和业务数据来源
4. 不为 V2 另建平行业务库表模型

在此前提下，V2 允许对实现方式做优化：

1. 调整分层
2. 优化命名
3. 合并重复逻辑
4. 优化接口结构
5. 优化任务拆分方式

### 4.4 接口与任务同等重要

V2 重构对象不仅包括接口，还包括：

1. 定时任务
2. 自动预警
3. 数据同步
4. 外部接口采集
5. 配置与调度开关

### 4.5 遇到问题先追旧后端

V2 开发时遇到问题，不先在新项目里猜实现，而是先去旧后端找对应处理方法，再决定是否沿用、简化或优化。

### 4.6 DTO/VO 隔离原则

#### 4.6.1 强制隔离范围

以下模块在 V2 中必须做 DTO/VO 隔离，不允许 Entity 直出直入：

1. 认证与当前用户
2. 用户、角色、菜单、字典、部门、组织、人员
3. 预警信息、预警指标、预警设施
4. 监测站点、监测项、防洪预案
5. 巡检记录、养护记录、值班安排、值班日志
6. 水雨情、大坝、位移历史、闸门等对外查询接口
7. 数据同步和自动预警涉及的人工触发或查询接口

其中“认证与当前用户”必须单独维护认证域 VO，不与后台用户管理详情 VO 混用，也不允许以前端方法重名掩盖两类不同语义。

#### 4.6.2 通用对象约束

1. 所有写接口必须定义请求 DTO，例如 `CreateDTO`、`UpdateDTO`、`AssignDTO`
2. 所有查询列表必须定义 `QueryDTO`，分页查询继承或复用通用分页 DTO
3. 所有响应必须返回 VO，例如 `DetailVO`、`ListItemVO`、`OptionVO`
4. 删除、批量删除、分配、重置密码等动作必须定义独立动作 DTO，不再依赖路径变量拼装业务语义
5. Entity 仅在 Service/Mapper 内部流转，不直接进入 Controller 对外契约

### 4.7 进度拆分粒度原则

为保证后续开发颗粒度可控，进度跟踪按以下规则执行：

1. 自 D 阶段起，默认采用“一个小阶段 = 一个接口”作为唯一开发粒度。
2. 这里的“一个接口”以“请求方法 + 路径”判定，例如 `GET /api/users/page` 与 `POST /api/users/create` 必须拆成两个独立小阶段。
3. 前端同一页面如果复用同一路径做普通查询和搜索，只记为一个接口阶段，不重复计数，例如 `GET /api/warnings/page`。
4. 非 HTTP 能力按“一个任务方法 = 一个小阶段”拆分，例如 `WarningAutoCheckTask.checkWarning`、`DataSyncTask.synflowData`。
5. 模块、页面、Controller、Service 只允许作为分组视图，不再直接作为进度项。
6. H 阶段属于联调与切换里程碑，可保留批次级跟踪，但不得回退替代 D-G 阶段的接口级拆分。

## 5. 旧后端参考策略

| 问题类型 | 旧后端参考位置 | V2 处理原则 |
| --- | --- | --- |
| 几何点位处理 | `WarningInformationServiceImpl`、`InspectionRecordsServiceImpl`、`MeasuringStationServiceImpl` | 参考旧实现方式，在 V2 中统一封装 |
| 认证、用户、角色、权限与数据源 | `UserDetailServiceImpl`、`UserServiceImpl`、`UserMapper`、`application.yml` | 先对齐旧项目数据库、表结构和数据源切换方式，再在 V2 中优化实现分层，不能改动数据库契约 |
| 权限和缓存清理 | `UserController`、`RoleController` | 参考角色分配、菜单分配后的缓存处理逻辑 |
| 外部位移/监测聚合 | `DisplacementHistoryService` | 参考外部接口聚合方式，V2 中可优化参数和返回结构 |
| 自动预警规则 | `WarningAutoCheckTask` | 参考阈值判断和预警生成方式，V2 中按模块重构 |
| 水雨情采集逻辑 | `WarningAutoCheckTask`、相关 Mapper | 参考数据来源与最新数据查询方式 |
| 闸门 SQL Server 特殊处理 | `DgqServiceImpl` 及同类实现 | 参考 JDBC 兼容方案，V2 中视情况保留或收敛 |
| 上传与导出 | `InspectionRecordsController`、`MtenceRecordController` | 参考旧处理经验，V2 中统一规范 |
| 数据同步 | `DataSyncTask` | 参考同步职责和同步入口，V2 中重新规划任务职责 |

## 6. 定时任务纳入说明

旧后端已存在定时任务能力，主要涉及：

1. 数据同步
2. 自动预警
3. 外部数据采集相关处理

因此 V2 重构时，定时任务必须和接口一起纳入设计范围，不能只完成接口迁移，而忽略依赖任务才能成立的业务能力。

V2 对旧定时任务的处理方式只保留四种：

1. 保留
2. 合并
3. 重写
4. 废弃

具体任务清单和迁移状态放在进度文档中跟踪，不在本设计文档中展开。
